# 紅白戦チーム分け Steering（product）

> 対象リポジトリ = basketball-coach-strategy。Spec は同ディレクトリの `requirements.md`／`design.md`／`tasks.md`。

## 体験仮説

中学バスケ部のコーチが体育館でスマホから30秒でバランスの取れた紅白戦チームを出せ、子供には評価が見えない。

## 対象ユーザー

- 主：部活のコーチ（テナントの owner ロール）。練習の合間に片手で操作する。
- 副：名簿を管理する管理者（isAdmin）。スプレッドシートを直し、アプリへ同期する。
- 画面を覗く子供は利用者ではない。名前とチームの文字以外を読めない作りにする。

## なぜ作るか

コーチは毎回、頭の中で Tier・役割・身長・学年・前回の組み合わせを勘案してチームを組んでいる。
この判断をエンジンに移し、コーチの行動を「出席を確認して分けるを押す」だけにする。
評価の根拠（Tier・役割）は子供に見せられない情報なので、アプリはそれを画面に一切出さない。

## 成功の物差し

- チーム分けにかかる時間：面を開いてから結果が出るまでの秒数（E2E の計測と、コーチの体感の聞き取り）。
- 同じ組み合わせの再発：直近3回の履歴に対する同チームペアの延べ数（エンジンの目的関数 P をそのまま使う）。
- 数値の非露出：面の HTML とデータ島に Tier・役割・身長・学年・平均・警告・評価が無いこと（E2E の DOM 実測）。

## 決まっている裁定

- 独立URL `/scrimmage` をホーム画面に追加して開く。練習計画の画面は変更しない。別 Firebase プロジェクトにしない。
- 名簿の正本は Google スプレッドシート「バスケ_選手名簿」。アプリは同期した写しだけを読む。
- 結果はチーム A／B／C と選手名だけ。Tier・役割・ポジション・身長・平均・警告・評価を出さない。
- 1人入れ替えは持たない。「もう一回」（seed+1）だけ。
- 実力は Tier + 0.5×(学年−1) で学年が高いほど優遇し、上限を置かない。制約は全て重み付き罰点。

## やらないこと

- スプレッドシートへの書き戻し、名簿編集画面、OAuth、ウェブ公開CSV、1人入れ替え。
