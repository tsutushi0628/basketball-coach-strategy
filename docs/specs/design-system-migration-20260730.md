# 押せる部品を意味ロール層へ付け替えるための棚卸しと適用計画

対象リポジトリ: basketball-coach-strategy（このリポジトリのルート）
共通基盤: firebase-kit の design-system を規律の参照元として使う。製品側の実装はこの文書の作成時点では読取のみ。

本文中のパスはこのリポジトリのルートからの相対で書く。
利用者ホーム配下の絶対パスは公開ドキュメントに置かない規律に従う。

この文書は棚卸しと段取りだけを扱う。
どの役割にどの色を当てるかは決めない。

役割の定義は確定しており、正本は2つある。
値と役割の対応は `ui/styles/tokens.css` の意味ロール層（11行目以降）、用途と見た目の規律は `docs/design-system/component-spec.md` である。
役割ごとの現物は `docs/specs/button-roles-20260730.html` にあり、同梱の `button-roles-20260730-tokens.css` はアクセント6変数だけを暗い赤系のプリセットへ差し替えた写しである。
既定と違う値が入っているのは意図的で、プリセットを通しても役割が弁別できることを見せるためのものである。

両者と実装を突き合わせた結果、着手前に判断が要る箇所が6件出て、すべて決着している（6節）。
役割の割り当ての確定版は3.7節にあり、全53型のうち役割が決まっていない型は0件である。

### この文書が写すものと写さないもの

デザイン定義は現在レビュー差し戻しを受けて改訂中で、選択中と確定を色以外の軸でも分ける方向、中立操作と破壊と移動を面の有無と形で分ける方向、識別を押せる部品の色規律とは別章へ切り出す方向の3点が変わる見込みである。

そこでこの計画には**役割ごとの到達点の値を写さない**。
面の色、枠の太さ、角丸、文字色といった規定は用途の正本だけが持ち、この計画は役割名と参照先ファイルで書く。
上の3点が入っても、この計画の書き換えは要らない。

いっぽう**改修前の実装が現にどう書かれているか**は写す。
どのプリミティブがどのファイルの何行目から引かれているかは付け替えの入力そのもので、定義の改訂では変わらない。
本文に出てくる変数名と行番号はすべてこちらである。

## 1. 確定したロール語彙と検証結果

段階0は完了している。
意味ロール層は `ui/styles/tokens.css` の色プリミティブ群の下（11行目以降）に追記済みで、用途の規律は `docs/design-system/component-spec.md` が正本である。

共通基盤のロール語彙をそのまま使わず、この製品側に役割を定義する方針が採られた。
共通基盤の `design-system/` は中間層の作り方の参照元としてだけ使い、色の実値は持ち込まない（`docs/design-system/component-spec.md` 冒頭）。

### 1.1 アクセントの受け皿を製品側に作った経緯

firebase-kit の意味ロール12種（`firebase-kit/design-system/tokens.css:324-335`）は、面の地、前景、罫線、反転面という中立色だけを持つ。
アクセントの塗りと、その塗りの上に乗る前景色に相当するロールは無い。
`--color-cta` は塗り色として定義されているが（同ファイル 39行）、対になる前景色ロールは定義されていない。

いっぽうこの製品の押せる部品でもっとも頻出する組み合わせは、アクセント塗りとその上の前景色の対だった。
改修前に使われていた箇所を挙げる。

| 箇所 | 宣言 |
|---|---|
| `ui/styles/base.css:13` | `.btn-primary{background:var(--orange);color:var(--orange-ink);border-color:var(--orange)}` |
| `ui/styles/base.css:19` | `.lvtab.on{background:var(--orange);color:var(--orange-ink);border-color:var(--orange)}` |
| `ui/styles/base.css:27` | `.daytab.on{background:var(--orange);color:var(--orange-ink);border-color:var(--orange)}` |

| `ui/styles/auth-page.css:28` | `.btn-primary{background:var(--orange);color:var(--orange-ink);border-color:var(--orange)}` |

| `ui/styles/pattern-timeline.css:283` | `.pk.on{background:var(--orange);color:var(--orange-ink);border-color:var(--orange)}` |

`--surface-inverse` と `--on-inverse` を流用すると、この製品の選択中の塗りが墨黒の反転面になる。
チームカラーの選択機能（16プリセット）が塗り替える対象がまさにこの塗りなので、反転面へ寄せるとその機能が意味を失う。

確定した割り当ては、アクセントの面塗りを「いま選ばれている印」の役割に専有させ、保存と適用の役割はアクセント以外の軸で立てるというものである。
根拠と具体の値は用途の正本が持つ（`docs/design-system/component-spec.md` のアクセント面塗りに関する章）。
選択中の表現を反転にする案はオーナー判断で差し戻されており、アクセントの深い側を保存に使う案も採られていない。
プリセットを通すとアクセント面上の文字が明暗どちらにも振れるため、アクセント系の面を2つの役割に分けると弁別が明度差だけに縮む、というのが採らなかった理由である。

保存と適用をどの軸で立てるかは改訂の対象に入っている（色以外の軸でも分ける方向）。
そのため本計画では軸の中身を書かず、役割名で参照する。

追記されたロールは42宣言で、押せる部品の5役割、文字だけの導線、焦点リング、対象識別、曜日を覆う。
フォーカスリングは `--focus-ring` の1つに役割化され、23箇所の手書き重複を畳む先ができた（重複の一覧は3.4節）。
エラー前景は破壊の役割の前景として役割化された。

### 1.2 ロールをリテラル値に畳んではいけない（実数で確認済み）

チームカラーの上書きは、6つのプリミティブだけを末尾の `:root` で再宣言する形で実装されている。

```js
// ui/color-presets.mjs:89-99
export function themeOverrideCss(themeKey) {
  if (themeKey === DEFAULT_THEME_KEY) return '';
  ...
  if (!THEME_KEYS.includes(themeKey)) return '';
  const theme = PRESET_THEMES[themeKey];
  const decls = ACCENT_VARS.map((v) => `${v}:${theme[v]}`).join(';');
  return `:root{${decls}}`;
}
```

再宣言される6つは `--orange`、`--orange-ink`、`--orange-soft`、`--orange-deep`、`--boys`、`--girls`（`ui/color-presets.mjs:46`）。
この上書きCSSは全部品CSSより後ろに連結され、先に出ている `:root` に後勝ちする（`functions/index.mjs:647-649,654`）。

CSSカスタムプロパティは計算値を求める時点で解決される。
だからロールを `--fill-accent: var(--orange)` の形で書けば、後から `:root` で `--orange` が差し替わってもロール経由の参照先に届く。
逆にロールをリテラルの色値で書くと、16プリセットすべてが静かに効かなくなる。
画面は壊れず色だけが既定に固定されるため、テストが色の実値を見ていない限り検出できない。

したがってロール定義はプリミティブへの間接参照を保つ。
これは「値はトークンだけ」の規律（`firebase-kit/design-system/component-spec.md` 横断規律1）と衝突しない。
ロール層とプリミティブ層の2段構成にして、部品はロールだけを参照し、ロールがプリミティブを参照する形になる。
同じ規律は製品側の正本にも「ロールの値はプリミティブへの参照だけで書く」として入っている（`docs/design-system/component-spec.md`「意味ロール層の規律」）。

追記済みのロール層がこの条件を満たしているかを機械的に確かめた。
満たすべき性質は4つで、いずれも成立している。

- **リテラルの色値が1つも無い**。16進数、`rgb()`、`hsl()`、`oklch()` のいずれも現れない。
- **参照先が定義されていない参照が1つも無い**。
- **面を持たない役割だけがキーワード（`transparent`）を値に持つ**。色の値を運ばないのでプリセットの差し替えに追従する必要がなく、`ui/styles/tokens.css` の層冒頭のコメントが明示的に除外している。
- **ロールがロールを参照する形が混ざっている**。識別ラベルの文字色が本文前景のロールを指しており、プリミティブまで2段でたどる。間接参照は保たれるが、検査は1段で止めず最後までたどる必要がある（8.2節の検査1）。

宣言の本数や内訳の件数はここに書かない。
定義側が改訂中でロールの増減と改名が続いており、本数を写すとこの計画のほうが先に古くなる。
上の4性質は改訂をまたいで成立していなければならない不変条件で、実数はそれを検査するテストの側に置く。

よって「ロールをリテラルに畳むと16プリセットが静かに壊れる」という条件は守られている。
守られ続けることを検査する形は8.2節に置く。

### 1.3 プリセットに追従するロールと固定されるロール

16プリセットが差し替えるのは6つのプリミティブだけなので（`ui/color-presets.mjs:46`）、ロールが追従するかどうかは「参照を最後までたどった先がその6つに入るか」で決まる。

追従するのは、選択中の面と枠と前景、見出しラベルとリンクの前景、焦点リング、男女の識別色の群である。
固定されるのは、それ以外のすべて。

役割ごとに見ると、**状態の群だけが追従し、確定と破壊と中立操作と移動の群は固定される**。
これがどのチームカラーでも確定だけが同じ見た目で立つという設計意図（`docs/design-system/component-spec.md`「アクセント面塗りを状態に割り当てた根拠」）と一致している。

ここで個々のロール名を列挙しない。
改訂で選択中の枠と確定の細線が改名されており、名前を写すと計画が先に古くなる。
どの変数がどちらに入るかは `ui/styles/tokens.css` を見れば参照先から機械的に決まるので、名前ではなく群と判定規則で書く。

面のロールと、その面の上に乗る前景ロールの追従性は、6つの役割すべてで揃っている。
片方だけが動く組は無い。
識別色は面だけを持ち、その上に文字を置かない形に決まったので（`docs/design-system/component-spec.md`「対象識別の色を状態の色に畳まない理由」）、対で追従性が食い違う余地がそもそも無くなっている。

## 2. トークンから本番まで届く1本の流れ

### 2.1 経路

トークンを直してから利用者の画面に出るまでは5段である。

1. `ui/styles/tokens.css` を編集する。
2. デプロイ時に `firebase.json:18-20` の predeploy が `npm --prefix "$RESOURCE_DIR" run build` を呼ぶ。
3. そのビルドが束ね直しとコピーを1コマンドで行う。
4. Cloud Functions 側が起動時にCSSをファイルから読み、HTMLの `<style>` へ文字列として埋め込む。
5. Hosting の全パスがその関数へ転送されるので、利用者はこの埋め込み済みHTMLを受け取る。

段3のコピーは手作業ではなくビルドスクリプトの一部である。

```json
// functions/package.json:10-12
"scripts": {
  "build": "npx -y esbuild@0.24.0 index.mjs --bundle --platform=node --format=esm --packages=external --outfile=dist/index.mjs && node -e \"const fs=require('fs');fs.rmSync('dist/styles',{recursive:true,force:true});fs.cpSync('../ui/styles','dist/styles',{recursive:true})\""
}
```

コピーが必要な理由は、束ね直したファイルから見た相対パスが変わるためで、その意図はローダー自身のコメントに残っている。

```js
// ui/styles/load-css.mjs:5-9
 * 相対パスで .css を読む。esbuild でバンドルされると `import.meta.url` は出力ファイル
 * （functions/dist/index.mjs）自身を指すようになるため、`./styles/xxx.css` のような相対解決は
 * バンドル後は `functions/dist/styles/xxx.css` を指すことになる。そのため `functions/package.json`
 * の build スクリプトで `ui/styles/` の内容を `functions/dist/styles/` へコピーしている
```

段4の埋め込み先は1箇所しかない。

```js
// ui/render-shared.mjs:654
<style>${BASE_CSS}${css || ''}</style>
```

段5の転送は Hosting の書き換え規則による（`firebase.json:23-37`。`"source": "**"` を関数 `render` へ、公開ディレクトリ `public` の中身は空）。

### 2.2 この経路が古い複製を残さない理由

`functions/dist/` は追跡対象から外れている（`.gitignore:14-15`）。
デプロイの前段でビルドが毎回走り、コピー先を消してから作り直す（上記 `fs.rmSync` に続く `fs.cpSync`）。
ローカル確認の入口も同じビルドを先に通す（`package.json:9` の emulate が `npm --prefix functions run build` から始まる）。
よって編集から確認、デプロイまでのどの経路にも、人が手でコピーする段は無い。

### 2.3 注入点は3つ、独立した色定義は最大2つ

トークンは3つのCSSに置かれたマーカーへ差し込まれる。

| ファイル | マーカー行 | 読み込み方 |
|---|---|---|
| `ui/styles/base.css` | 2行目 `:root{/*TOKENS*/}` | `ui/render-shared.mjs:40` |
| `ui/styles/auth-page.css` | 6行目 `:root{/*TOKENS*/}` | `ui/login.mjs:20`（参加ページも同じ定数を共有） |
| `ui/styles/picker.css` | 6行目 `:root{/*TOKENS*/}` | `ui/tenant-picker.mjs:20` |

3つとも同じ `ui/styles/tokens.css` を差し込む。
よってロール定義を `tokens.css` に足せば、練習計画本体とログイン系ページとテナント選択ページの3系統に同時に入る。
ページごとに書き足す作業は発生しない。

1つのHTMLに出る `:root` の数は最大2つである。
既定テーマでは `base.css` 由来の1つだけ、既定以外のプリセットではチームカラー上書きの1つが加わって2つになる。
ログインページ、参加ページ、テナント選択ページはチームカラー上書きを受け取らないので常に1つである。

### 2.4 本番の連結順（前提の訂正）

同一の `<style>` タグ1つのなかで、次の順に連結される。

| 順 | 内容 | 根拠 |
|---|---|---|
| 1 | `ui/styles/base.css`（トークン差し込み済み） | `ui/render-shared.mjs:40,654` |
| 2 | `ui/styles/pattern-timeline.css` | `ui/pattern-timeline.mjs:787,873` |
| 3 | `ui/styles/editor.css` | `ui/editor.mjs:36` を経て `ui/pattern-timeline.mjs:873` |
| 4 | `ui/styles/goal-editor.css` | `ui/goal-editor.mjs:40` を経て同上 |
| 5 | チームカラー上書き | `functions/index.mjs:649,654` |
| 6 | `ui/styles/auth-client.css` | `ui/auth-client.mjs:336` を経て `functions/index.mjs:654` |

本作業の前提として渡された「base、pattern-timeline、editor、auth-client」の順は、`docs/specs/editor-layout-20260730.html:9-12` のプレビュー用の読み込みに対応する。
本番ではこれに `goal-editor.css` とチームカラー上書きの2つが加わる。
プレビューは別々の `<link>` だが本番は単一の `<style>` 内の文字列連結で、どちらも同一詳細度なら後勝ちという点は同じである。

`ui/styles/picker.css` と `ui/styles/auth-page.css` はこの並びに一度も現れない。
別ルートの別HTMLで単独の `<style>` として出る。
したがって全7ファイルが1画面に同居する状況は存在しない。

`ui/index.html` は `npm run build:static`（`package.json:6` から `ui/build.mjs:107-111`）が書き出す静的プレビューで、本番の配信経路からは参照されない。
中の `<style>` は生成時点の `base.css` とトークンの写しなので、`tokens.css` を直すと内容が古くなる。

## 3. 押せる部品の付け替え対象

### 3.1 総量

`ui/styles/` 配下は8ファイル835行。
`tokens.css` は変数宣言だけで押せる部品のセレクタを持たない。
残る7ファイルに押せる部品のセレクタが145件ある。

付け替えの単位は色系の宣言行である。
押せる部品と、フォーカスや無効状態のレシピを共有する対話コントロール（入力欄、選択、テキスト領域、状態テキスト、スクリム、読込中表示）を範囲に取ると、色系宣言を持つ行は109行になる。

| ファイル | 総行数 | 押せる部品セレクタ | 色系宣言行 |
|---|---|---|---|
| `ui/styles/base.css` | 265 | 33 | 18 |
| `ui/styles/pattern-timeline.css` | 311 | 30 | 21 |
| `ui/styles/auth-client.css` | 65 | 29 | 25 |
| `ui/styles/editor.css` | 73 | 20 | 18 |
| `ui/styles/auth-page.css` | 50 | 13 | 12 |
| `ui/styles/goal-editor.css` | 29 | 11 | 11 |
| `ui/styles/picker.css` | 33 | 9 | 5 |
| `ui/styles/tokens.css` | 9 | 0 | 0（定義側） |
| 合計 | 835 | 145 | 109 |

109行のうち、値がキーワードだけの行は2行である（`ui/styles/base.css:257` の印刷時の透明化、`ui/styles/pattern-timeline.css:305` の `stroke:currentColor`）。
残りはすべて `var()` 経由でプリミティブを参照している。
生の16進数を直書きしている押せる部品は1つも無い。

つまりこの製品の課題は「トークンを使っていない」ことではない。
24個のプリミティブが意味の層を持たないまま、部品側から直接引かれていることである。

`docs/findings/button-inventory-20260730.md` は同じ7ファイルについて、プリミティブを直参照している色の宣言を375件と数えている。
数え方が違うだけで矛盾はしない。
あちらは押せる部品に限らずカードや時間割の面も含めた全ての宣言を1件ずつ数えており、こちらは押せる部品と対話コントロールに絞って宣言を含む行を数えている。
独立に全宣言を数え直すと396件になった（差は数える色属性の範囲による）ので、規模の桁は一致している。
付け替えの進捗を全体で測るなら375件を分母に、押せる部品の作業量を見るなら109行を使う。

範囲に8つ目の所在がある。
一覧画面の行リンクは `ui/styles/` ではなく `ui/build.mjs:100-106` のインラインCSSに書かれていて、面と枠と文字色をプリミティブから直に引いている。
同ファイル:97 には要素へ直書きした文字色もある。
この製品の押せる部品を全部ロール経由に寄せるには、7つのCSSに加えてこのビルドスクリプトも対象に入れる。
棚卸し文書の375件も7ファイルだけを数えているので、同じ抜けがある。

### 3.2 見た目の系統分けは別文書が正本

改修前の見た目をいくつの系統に分けるかは、`docs/findings/button-inventory-20260730.md` が正本である。
面塗り、枠線、文字色の3点で数えて8系統で、確定した定義のもとでは7系統へ収束する。
8系統から7系統への対応と、押せる部品53型の役割別の一覧も同じ文書にある。

系統の分類をこの文書で重複して持たない。
同じものを2通りに数えた表がリポジトリに並ぶと、実装者がどちらに従うか判断できなくなる。
本節は系統分けを前提として受け取り、付け替えの段取りに必要な2点だけを足す。

第一に、系統は改修前の見た目でまとまっており、役割は押した結果の性質でまとまっているので、対応は多対多になる。
1つの系統が最大3つの役割を運んでいた。
したがって付け替えを系統単位で進めると、1コミットで複数の役割が中途半端に動く。
役割単位で進める根拠がここにある（5節の段階3）。

第二に、系統の一覧を実装と突き合わせて2点の補いが要る。

- **枠線が透明な部品と枠線が無い部品を分けて扱う**。正本の一覧では削除系の2部品が「透明1px」の系統に入っている（`ui/styles/editor.css:40,45`）。破壊の役割には枠線のロールが用意されているので、この2部品の透明な枠は付け替えで扱いが変わる。枠線が無い部品と同じ扱いにすると、この変化を見落とす。定義側は中立操作と破壊と移動を面の有無と形で分け直す改訂に入っているため、透明枠と枠なしの区別は台帳の側で持ち続ける。
- **動画リンクの面はページ地でカード面ではない**。正本の一覧は `ui/styles/base.css:134` をカード面の系統に置いているが、実際の宣言は `background:var(--bg)` でページの地色である。役割の割り当て（文字導線）は変わらないので実害は無いが、面の値を移すときに参照先を間違えないよう記しておく。

### 3.3 いま見えているプリミティブをどのロールへ読み替えるか

付け替えの実作業は「いまここに書かれているプリミティブを、どのロールへ置き換えるか」の判断の連続になる。
その判断は**2つを決めれば一意に定まる**。その宣言が属する部品の役割（3.7節で確定）と、その宣言が担っている見た目の要素である。
役割と要素が決まれば、参照すべき変数は `ui/styles/tokens.css` の該当役割のブロックから引ける。

ロール変数の名前をこの表に写さない。
改訂で選択中の枠と確定の細線が既に改名され、中立操作と移動の参照先も動いている。
名前を写すと表が実態より先に古くなり、実装者が存在しない変数を書く。

要素は5種類しかない。

| 要素 | 現行の書き方 | 決め方 |
|---|---|---|
| 面 | `background` / `background-color` | 役割の面のロール |
| 枠 | `border` 系の色 | 役割の枠のロール |
| 前景 | `color` / `fill` / `accent-color` | 役割の前景のロール |
| hover の面と前景 | `:hover` 内の上記 | 役割の hover 用ロール（無い役割は休止と同じ） |
| 焦点リング | `outline` | 全役割共通の焦点リングのロール（3.4節） |

いま出てくるプリミティブがどの要素に当たるかは次のとおりで、これは改修前の実装の事実なので改訂では動かない。

| 現行プリミティブ | 押せる部品でどの要素に出るか |
|---|---|
| `--surface` | 休止状態の面、暗い面の上の前景 |
| `--bg` | ページの地、hover の面 |
| `--ink` | 本文相当の前景、強い面 |
| `--mute` | 補助の前景、無効時の面 |
| `--hair` | 弱い側の枠 |
| `--line-2` | 濃い側の枠、hover の枠 |
| `--scrim` | 覆いの暗幕（押せる部品ではない） |
| `--orange` | 選択中の面と枠、焦点リング、hover の前景 |
| `--orange-ink` | 選択中の面の上の前景 |
| `--orange-deep` | 見出しラベル、リンク、開閉トリガの前景 |
| `--terra` / `--terra-ink` | 破壊の前景 |
| `--boys` / `--girls` | 男女の識別色の面 |
| `--sat` / `--sun` | 土日の前景 |
| `--sat-soft` / `--sun-soft` | 土日の淡い面 |
| `--sw-main` / `--sw-2nd` | 色見本の面（ロール化しない） |

単純な置き換えにならないものが4つある。

**hover の前景にアクセントを使っている8箇所**（`ui/styles/base.css:11`、`auth-page.css:24`、`auth-client.css:6`、`:55`、`editor.css:37`、`:41`、`goal-editor.css:4`、`:17`）は、役割ごとに hover の振る舞い自体が変わる。
ロール名の入れ替えではなく規則の差し替えになる。

**`--orange-soft`** の3用途（確定の無効時 `ui/styles/auth-page.css:30`、読込中表示の輪 同`:44` と `auth-client.css:57`、行リンクの hover 枠 `picker.css:19`）は、無効時が役割2の無効用ロールに引き取られ、残る2つは押せる部品の外にある。
ロール化しないままでも段階3は進む。

**`--girls-ink`** は用途自体が無くなる（6節の不整合1）。

**`--sw-main` と `--sw-2nd`** は `ui/styles/tokens.css` に定義が無い（`ui/styles/auth-client.css:41,44,45,47` が参照している）。
色見本ごとに要素側で注入される前提の変数なので、ロール層へ移すのではなく注入の仕組みをそのまま残す。

## 4. クラス同居の解消

### 4.1 いま起きていること

`ui/editor.mjs:596` が1つの要素に2つのクラスを付けている。

```js
return '<div class="modetoggle ed-field" role="group" aria-label="男女オンリーの切り替え">'+
```

両者の宣言は `display` の値が食い違う。

```
ui/styles/base.css:33    .modetoggle{display:inline-flex;gap:6px;background:var(--bg);border:1px solid var(--hair);border-radius:999px;padding:4px}
ui/styles/editor.css:8   .ed-field{display:flex;flex-direction:column;gap:4px;margin-bottom:12px}
```

詳細度はどちらも同じで、`editor.css` は `base.css` より後ろに連結される（2.4節の順3と順1）。
よって `.ed-field` の縦積みが勝ち、3択トグルが横並びにならない。

### 4.2 採る方法

3つの案のうち、クラスを分ける案を採る。

**採用案（クラスを分ける）**
`ui/editor.mjs:596` の `ed-field` を、余白だけを持つ別クラスに差し替える。
`ui/styles/editor.css` に `margin-bottom:12px` だけを持つ1宣言を足す。
`ui/styles/editor.css:8` の `.ed-field` は変更しない。

**却下した案1（要素を分ける）**

### 不整合1: 女子の面と文字色の追従性の食い違い（解消済み）

**この項目は解消されている。記録として残す。**

当初のロール層は識別色の面と文字色をこう組んでいた。

```
--team-girls-fill:var(--girls); --on-team-girls:var(--girls-ink);
```

`--girls` はプリセットの差し替え対象だが、`--girls-ink` は対象外である（`ui/color-presets.mjs:46` の6変数に含まれない）。

影響は改修前の実装にも出ていて、`ui/styles/base.css:157` の進行中チップが16プリセット全てで文字と面の明暗差4.5対1を満たしていない（既定テーマで1.42対1、もっとも差が付くプリセットでも4.15対1）。

--team-boys-fill:var(--boys); --team-girls-fill:var(--girls);
--on-team-label:var(--on-surface);

識別ラベルの文字は識別色の上ではなく面の側に置き、識別色は面としてだけ添える（`ui/styles/tokens.css:60-65`、`docs/design-system/component-spec.md`「対象識別の色を状態の色に畳まない理由」）。

対で追従性が食い違う余地がそもそも無くなったので、値をどう選ぶかの判断も要らなくなった。

**付け替え側に1つ作業が増える。**

### 不整合3: 日ピッカーの部品が役割1と役割5の両方に現れる

規律は役割1に「日付ピッカーの日」を、役割5に「日送り、週送り、月送り」を置いている。
実装では送り専用のボタンが存在せず、期間の選択肢そのものが送りを兼ねている。
4つの変種がすべて `.pk` を土台にしている。

| 生成箇所 | クラス | 用途 |
|---|---|---|
| `ui/pattern-timeline.mjs:804` | `pk cal-go` | 日ピッカーの曜日ボタン |
| `ui/pattern-timeline.mjs:814` | `pk cal-go-dayweek` | 日レベルの週セレクタ |
| `ui/pattern-timeline.mjs:824` | `pk cal-go-week` | 週セレクタ |
| `ui/pattern-timeline.mjs:834` | `pk cal-go-month` | 月セレクタ |

4つとも現在の選択を `.on` で示し、選択中の見た目は `ui/styles/pattern-timeline.css:283` の1規則が担っている。
役割1と役割5の見た目を同じ土台に同時に当てることはできず、規律自身の「1つのロールは1つの役割にしか使わない」（`docs/design-system/component-spec.md`「意味ロール層の規律」）にも反する。

**裁定1**：4つとも土台は移動に置き、いま表示している対象にだけ状態の印を重ねる。
コーチの操作としては「押すとその期間へ飛ぶ」が本体で、いま居る場所に印が付いているのは結果の表示だからである。

同じ土台を共有していても破綻しない。
土台が移動、重ねる印が状態という二層に分かれるので、「1つのロールは1つの役割にしか使わない」の規律も守られる。
付け替えの実作業では、土台の宣言（`ui/styles/pattern-timeline.css:280`）を移動のロールへ、選択中の宣言（同`:283`）を状態の印のロールへ、別々に移す。
この2行は段階3の別の回で触ることになるので、間の期間は土台だけが移動の見た目で印が旧来のままになる。

## 8. 期待値の更新が必要なテスト

### 8.1 色の参照先だけを差し替える場合

段階3はクラス名も要素IDもDOM構造も変えない。
変わるのは色系宣言の右辺と、その結果として一部の役割の見た目である。
したがってクラス名やIDやDOM構造を見ているテストは影響を受けない。

必ず更新が必要なのは1ファイルの2行である。

```js
// ui/toolbar-reorg.test.mjs:108
assert.match(BASE_CSS, /\.lvtab\.on\{background:var\(--orange\)/, '表示単位タブの選択中はこの製品の選択中色(オレンジ)で塗られる');
// ui/toolbar-reorg.test.mjs:109
assert.match(RENDER.css, /\.pk\.on\{background:var\(--orange\)/, '日付ピッカーの選択中はオレンジ塗りを維持');
```

この2行はCSSの文字列そのものを照合している。
検証している業務意図（選択中は選択中色で塗られる）は変わらないので、参照するトークン名だけをロール名へ替える。

条件付きで更新が要るのが2ファイルある。

- `ui/block-tint.test.mjs:20-24`：区分の色に使えるトークン名の許可リストを持つ。区分の色をロール経由に変える場合だけ、このリストを広げる。3.3節のとおり区分の色は製品側に残す方針なので、その場合は更新不要。
- `ui/color-presets.test.mjs:26,28`：チームカラーが上書きする6つと、上書きしてはいけない構造側のトークンを列挙している。1.2節の方針（上書き対象は6プリミティブのまま）を採るなら更新不要。ロールを上書き対象に加えるなら、この列挙を広げる必要がある。このテストはチームカラー機能を守っている検査なので、方針を変える場合は先にここを直す。

計算値を見ているテストは2箇所あるが、どちらも色ではない。
`ui/aim-multiline.test.mjs:109` は改行の扱い、`ui/toolbar-reorg.test.mjs:129` は表示形式である。

### 8.2 チームカラーが効き続けることを捕まえる検査

守るべき性質は「アクセントに依存するロールが16プリセットで実際に動き、墨に依存するロールは動かない」ことである。
これが崩れたときの症状は、画面が壊れず色だけが既定に固定されることなので、色の値を見る検査がないと気付けない。

**結論は拡張で、対象は `ui/color-presets.test.mjs` である。**

新設にしない理由は、このファイルが既に同じ不変条件の一段下を持っているためである。
`ui/color-presets.test.mjs:26` の `ACCENT_VARS` がプリセットの差し替え対象を、`:28` の `STRUCTURAL_VARS` が差し替えてはいけない構造側を列挙している。
ロールの追従性はこの区別をロール層へ持ち上げたものなので、別ファイルへ割ると1つの規則が2箇所に分かれ、片方だけ直される。

検査は3本立てる。

**検査1（形）**：ロール層の全宣言が、`var()` による参照か、面を持たない役割の `transparent` のどちらかであることを確かめる。
リテラルの色値が1つでも現れたら落とす。

参照は1段で止めず、プリミティブに着くまでたどる。
ロールが別のロールを指す形が既に1件あるので（`--on-team-label`、1.2節）、1段だけを見る検査は入れ子を「プリミティブではない」と誤判定する。
たどる途中で同じ名前に戻ったら循環として落とし、どこにも定義されていない名前に着いたら宙ぶらりんの参照として落とす。
綴り違いは宣言を無効にして色を継承値へ落とすので、これも静かな故障の一種である。

期待値は1.2節の4つの不変条件をそのまま書く。
リテラルの色値が0、参照先の無い参照が0、キーワードを持つのは面を持たない役割だけ、参照は最後までたどれる。
宣言の本数や内訳の件数は期待値に入れない。
定義側でロールが増減しても本数だけで落ちる検査は、通すために期待値を書き換える手間しか生まない。

**検査2（追従性）**：16プリセットそれぞれについて、ロールを最後までたどって解決し、値が既定から動くロールの集合を求める。
その集合が**状態、識別、文字導線、焦点リングの4群だけ**であり、確定と破壊と中立操作と移動の4群が1つも含まれないことを確かめる（1.3節）。
押せる部品の5役割のうち追従するのは状態だけで、そこが崩れると確定がチームカラーで動いて状態と混ざる。
判定は変数名の接頭辞で行う。
どの群に属するかは接頭辞に出ているので、ロールが増えても新しいロールが自動的に正しい側へ分類される。

期待する集合はテスト側に書き、`ui/styles/tokens.css` から導出しない。
検査対象から期待値を作ると、定義を誤って変えても落ちなくなる。

**検査3（面と前景の対）**：同じ役割の面ロールが追従するなら、その面の上に乗る前景ロールも追従することを確かめる。
面だけが動いて文字色が既定に固定されると、特定のプリセットで文字が読めなくなる。
これがまさに「色だけ既定に固定される」故障の形である。

現在は6つの役割すべてで対の追従性が揃っているので、この検査は今のまま通る。
つまり期待値の決定を待たずに退行を止める柵として先に入れられる。
実際にこの形の食い違いが一度発生して正本側で直っているので（6節の不整合1）、再発を止める価値がある。

ブラウザは要らない。
プリミティブの解決は文字列の置き換えで決定論的に計算できるので、既存のテストと同じ枠組みで足りる。
実描画の計算値まで見る検査は、段階3が全て終わったあとに1本だけ足せばよい。
