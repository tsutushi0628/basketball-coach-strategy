# 過去の週への移動とコピー元選択の行動分析

対象リポジトリ: basketball-coach-strategy（このリポジトリのルート）。
本文中のパスはリポジトリのルートからの相対で書く。

この文書は、service-design.md（裁定反映済み）の2要望をコーチの身体動作に落とし、モック（mock-week-nav.html、mock-copy-source.html）の根拠と全状態パターンを渡す。
アプリ本体のコードは変更していない。

## 0. 結論

**要望1（過去の週）**: 週タブの4枠はいまのまま、列の左右に「前の週」「次の週」、列の直上に「年月で飛ぶ」と「今週へ戻る」を足す。
1週戻るのは親指1回で済み、去年の同じ時期へは年月の選択2回で届く。
「今週へ戻る」は表示中の週が今週でないときに現れ、現れても他の要素は動かない。
414px未満では一歩移動を列の上段へ回し、列に全幅を渡す。

**要望2（コピー元）**: 「他の日からコピー」の中を「おすすめ」（最大3件、行全体が押せるラジオ）と「探す」（年月と日の2段の選択）に分ける。
いちばん多い場面（直近の同じ曜日を持ってくる）は、行を1回押して取り込みボタンを1回押す2タップで終わる。
現状の select 全件一覧は保存済みの日が増えるほど一覧を送る量が増えるが、新しい形はどちらの枠も候補が定数に収まる。

設計文書との差分は3点で、4章にまとめた。

## 1. 要望1 過去の週を選べる

### 1.1 利用コンテキスト

| 項目 | 分析 |
|---|---|
| 誰が | バスケ部コーチ1人。毎週使い、画面の並びは体で覚えている |
| いつ | 場面A 日曜夜か月曜朝（今週を組む前に先週を見返す）／場面B 大会の3〜4週前（去年の同じ時期を見返す）／場面C 練習の翌日以降（記録の補填） |
| どこで | 場面AとCは自宅のソファか布団で、右手だけでスマホを持つ。場面Bは自宅の机のPCか、体育館の隅で膝の上のノートPC |
| どの幅で | 320 / 375 / 414 / 768px。身体動作フローは320pxで成立させる（後述）。PCは768px以上で、列が1段に収まる |
| なぜ | 先週の続きを決める、去年の山の作り方を今年に写す、書き忘れた記録を残す |
| どのくらい | 場面Aは1〜2分（1週戻って読んで戻る）。場面Bは5〜10分（去年の複数週を見比べる）。場面Cは3〜5分（1週戻って1日入力する） |

移動の距離は場面で違う。
AとCは1〜2週、Bは約52週である。
一歩移動だけだと場面Bで52回押すことになり、年月の選択だけだと場面Aで「先週」を選ぶのに年月を経由する。
2つの手段を両方置くのは、この距離の二峰性による。

### 1.2 カスタマージャーニー

#### 意図のフロー

```
場面A 先週の振り返り
  認知「今週どう組もう」→ 動機「先週どこまでやったか見たい」→ 行動開始 アプリを開く
  → タスク遂行 1週戻る → 火曜と土曜を読む → 結果確認「ここまでやった」
  → 行動変容 今週へ戻って今週の火曜を組む

場面B 去年の同じ時期
  認知「新人大会まで3週」→ 動機「去年の3週前はどう組んだか」→ 行動開始 PCで開く
  → タスク遂行 去年の11月へ飛ぶ → 週を送って3週前を探す → 上書きのある日を読む
  → 結果確認「去年はセットの確認を2回入れた」→ 行動変容 今週へ戻り、コピー元（要望2の「去年の同じ頃」）で持ってくる

場面C 記録の補填
  認知「先週の木曜、書き忘れてた」→ 動機「忘れないうちに残す」→ 行動開始 スマホで開く
  → タスク遂行 1週戻る → 木曜を押す → 「この日の記録を入力する」→ 入力して保存
  → 結果確認 保存した日がそのまま見えている → 行動変容 今週へ戻る
```

#### 身体動作フロー（場面A、片手スマホ、320px）

右手だけでスマホを持ち、親指で操作する。
親指の楽な可動域は画面の下半分で、上端の部品には親指を伸ばして届く。

1. ホーム画面からアプリを開く（1.5秒）。初期表示は今日に最も近い練習日。視線は画面中央の日ヘッダ。
2. 視線を上へ動かし、週タブ列の上段左端の「前の週」を見る（0.5秒）。列の上段は画面上部にあり、親指を伸ばしてタップする（0.4秒）。持ち替えはしない。
3. 4枠が1週ずれ、先頭「2026/08/23〜」がオレンジになる。同時に曜日帯が 08/23 週へ切り替わり、その週の先頭練習日が見える。「今週へ戻る」が年月の右に現れる。視線は列から曜日帯、日ヘッダへと縦に落ちる（1秒）。
4. 曜日帯で読みたい曜日（火）をタップする（0.4秒）。曜日帯はいまと同じ位置で、親指の位置もいままでと同じ。
5. 日ヘッダとタイムラインを読む（20〜60秒）。親指で下へスクロールする。
6. 読み終えて上へスクロールし、「今週へ戻る」をタップする（0.5秒）。今週の直近の練習日が見える。

合計のタップは3回（前の週、曜日、今週へ戻る）で、指の移動は上端と曜日帯の往復だけである。
「前の週」を列の上段の左端に置くのは、手順2で視線が列の左から入り、選択中の先頭枠（左端）と「前の週」が同じ側にあると、戻った週が左端に現れることと押した場所が一致するからである。

#### 身体動作フロー（場面B、体育館の隅でノートPC、768px以上）

立ったまま、または膝の上でノートPCを開き、トラックパッドで操作する。
両手は使えるが、体は落ち着かない。細かなドラッグや長いスクロールは向かない。

1. ブラウザで開く（3秒）。日レベル。視線は週タブ列。
2. 「年月で飛ぶ」の選択をクリックし、開いた標準の一覧から「2025年11月」をクリックする（2回クリック、2秒）。一覧は11件で、スクロールしなくても全部見える。
3. 窓が 2025/11 の第1週に合い、先頭枠がオレンジになる。曜日帯と日がその週の先頭練習日へ切り替わる（1秒）。
4. 「次の週」を2回クリックして第3週へ進む（1秒）。列の右端の位置は窓が動いても変わらないので、ポインタを置いたまま連続で押せる。
5. 曜日帯で火曜と木曜を順にクリックして読む（1〜2分）。
6. 「今週へ戻る」をクリックする（0.5秒）。

年月の選択を標準の select にするのは、体育館ではポインタの精度が落ち、独自のカレンダー部品より OS の一覧のほうが大きな当たりで選べるからである。
スマホでも同じ理由で、OS のピッカーが画面下半分に出て親指で回せる。

#### 身体動作フロー（場面C、片手スマホ、320px）

1〜5は場面Aと同じ。
6. 曜日帯で木曜をタップすると「この日の記録はありません。」と「この日の記録を入力する」の1つの導線が出る。導線は空状態の箱の中央で、親指の可動域に入る（0.4秒）。
7. 編集パネルが開く。見出しに「2026/08/27（木）」が出ているので、今週の木曜と取り違えていないことをここで確かめられる。
8. 入力して「保存」を押す（2〜4分）。保存後もこの日がそのまま見えている（service-design.md 2.5節。再読込の廃止が前提）。
9. 上へスクロールして「今週へ戻る」をタップする。

### 1.3 B=MAT分析

| ステップ | Motivation | Ability | Trigger | ボトルネック |
|---|---|---|---|---|
| A2 前の週を押す | 高い。今週を組む直前で「先週」を見たい気持ちが強い | 物理: 上端への親指1回。認知: 「前の週」の語が行き先を示す | 列の左端に語つきで常時あるので探さない | なし。現状はここに入口が無く、動機があっても行き場が無かった |
| A3 戻った週の日を見る | 高い | 物理: 0。認知: 先頭枠がオレンジになり、曜日帯と日が一緒に変わるので、いまどの週かを3箇所で読める | 変化が縦に並んで見える | 曜日帯と日が変わらないと「押せていない」と誤解する。3箇所が同時に変わることが要件 |
| A6 今週へ戻る | 中。読み終えて満足しており、戻る動機は「元に戻したい」程度 | 物理: 上端への親指1回。認知: 語で行き先が読める | 過去にいるあいだだけ現れるので、それ自体が「いま今週にいない」の合図 | 現れる場所が動くと探す。枠を常時予約して位置を固定する |
| B2 年月で飛ぶ | 高い。年に数回だが「去年どうしたか」は強い動機 | 物理: クリック2回。認知: 選択肢は到達範囲の年月だけなので「無い月」を選ぶ失敗が起きない | 列の直上に語つきで常時ある | 選択肢に範囲外の月が混ざると空の週に落ちる。到達範囲で絞ることが要件 |
| B4 次の週を送る | 中 | 物理: 同じ位置を連続クリック。認知: 0 | 右端の記号と語 | ボタンが窓の位置で動くと連打できない。列の左右端に固定する |
| C6 記録を入力する | 中。忘れないうちに、の切迫感 | 物理: 1タップ。認知: 「記録はありません」で過去の空の日だと分かる | 空状態の箱の中に導線が1つ | 導線が2つ（入力する、叩き台）だと過去の日で叩き台を選んで既習が矛盾する。過去は1導線に絞る |
| C7 見出しで日付を確かめる | 低い。確かめる動機は薄い | 認知: 見出しに日付と曜日がある（既存） | 「今週へ戻る」が出ていることが「過去にいる」の手がかり | 取り違えは起きうる。起きたら既存の削除で戻す |

Abilityの最大のボトルネックは、320pxで一歩移動と4枠が同じ段に収まらないことである。
4枠のラベル「2026/08/30〜」は14px太字で1枠が約124px幅になり、320pxの本文幅284pxには2枠しか並ばない（いまも2段2枠で折り返している）。
その左右に44pxの一歩移動を足すと1段1枠の4段になり、一歩移動の幅を詰めても収まらない。
そこで414px未満では一歩移動を列の上段へ回し、列に全幅を渡す。
これは曜日帯の週送りで既に採った取引（docs/design-system/component-spec.md「状態の部品の並べ方」）と同じで、代償は列の開始位置が44px＋7px下がることである。
414px以上では列の左右端へ戻す。

DOMの順は「前の週、列、次の週」で固定し、414px未満は並び順（order）だけで上段へ回す。
狭幅ではタッチが主でTabキーは使わないので、視覚順とTab順のずれは広幅で起きないほうを採った。

### 1.4 エッジケースとストレスケース

| ケース | 検討結果 |
|---|---|
| 到達下限（最古の上書き週か今週の4週前の早い方） | 「前の週」を押せない状態にする。消さない。文字と記号は死に色に沈み、枠は元々無いので無いまま（component-spec.md「押せない」行）。列の位置は動かない。年月の選択肢もその月が最古 |
| 未来上限（今週＋3週） | 「次の週」を押せない状態にする。扱いは下限と同じ |
| 上書きなしの過去週の日 | 「この日の記録はありません。」と「この日の記録を入力する」の1導線。叩き台の導線は出さない。空状態の箱は現状の .emptystate、導線は現状の .btn |
| 年度外の週（週キーの月曜が今日と別の学校年度） | 月の目標セルを出さず、週のセルを全幅にする。窓の中で年度をまたぐ枠（例: 2026/03/29〜 と 2026/04/05〜）では、選ぶ枠ごとに月セルの有無が変わる。目標バーは日の上にあり、変わっても列と曜日帯の位置は動かない |
| 年月で飛んだ先の月に上書きが無い | 全日「記録なし」。下限が「最古の上書き週」か「4週前」なので、範囲内の空の月は下限付近の高々4週に限られる。許す |
| 連続操作（前の週を連打） | 窓が1週ずつ滑り、ボタンの位置は変わらない。下限に着いたら押せなくなり、連打がそこで止まる。押すたびに曜日帯と日が変わるので、行き過ぎに気づける |
| 中断と復帰 | 過去の週を見ている途中で画面を閉じて戻ると、初期表示は今日に最も近い練習日（既存）。過去の週の位置は覚えない。場面AとCは1〜2週なのでもう1回押せば戻れる。場面Bは年月で飛べば1回で戻れる |
| 想定外の量（1年分の週を描く） | 描画量は到達範囲で上限がつく。まとめて描くか必要な週だけ描くかは architect の判断（service-design.md 2.6節） |
| エラー後（過去の日の保存に失敗） | 既存のパネル脚のメッセージのまま。入力は保持される |
| 初回と習熟 | 初回は「前の週」「今週へ戻る」の語で読める。習熟すると位置で押すので、状態で位置が動かないことが効く |
| 焦っているとき（練習直前に去年を見たい） | 年月で飛んで一歩移動で寄せる。最短で選択2回と一歩2回 |
| 週起点未設定のテナント | 実日付が無いので週ナビを出さない（現状の単一週のまま） |
| 日レベルと週レベルの食い違い | どちらの列を押しても selectWeek 1箇所で両方が揃う（ui/render-shared.mjs）。窓の移動も同じ持ち場に載せる |

### 1.5 UIデザイナーへのインプット

#### レイアウト制約（行動分析から導出）

- 週タブ列（.picker、.pk）の見た目、大きさ、並び、ラベル「yyyy/mm/dd〜」、4枠は変えない。
- 「前の週」「次の週」は列と同じ容器の左右端に置き、窓の位置で場所が動かない。414px未満では列の上段の左端と右端。414px以上で列の左右端。
- 「今週へ戻る」は年月の右に常時枠を予約し、見えないときも同じ幅を持つ。現れても年月の選択も列も動かない。
- 「前の週」「次の週」は到達端で押せない状態にし、消さない。
- 「年月で飛ぶ」は列の直上に置き、列自体をドロップダウンにしない。選択肢は到達範囲内の年月だけ。
- 一歩移動と「今週へ戻る」は移動ロール（面なし、枠なし、語つきピル、11px 700、SVG 19px）。年月は入力部品（.ed-sel 流用、高さ44px）。新しい色は足さない。
- 空状態の導線は過去週で1つ。導線の数が状態で変わっても、空状態の箱の位置は変わらない。
- 320 / 375 / 414 / 768px のどの幅でも横スクロールが出ない。実測は ui/e2e/evidence の JSON（5章）。

#### 全状態パターン（mock-week-nav.html の節番号）

1. 今週を含む窓で今週を選んでいる（日レベルと週レベルの両方の列）。
2. 「前の週」を1回押した後。「今週へ戻る」が現れている。
3. 過去週の上書きあり日。目標バーは2セル。
4. 過去週の上書きなし日。「この日の記録はありません。」と1導線。
5. 到達下限で「前の週」が押せない。
6. 未来上限で「次の週」が押せない。
7. 「年月で飛ぶ」を開いた状態。選択肢は到達範囲内だけ。
8. 今日と同じ年度の過去週の目標バー（2セル、月のセルはその週の月）。
9. 前の年度の週の目標バー（週のセルだけ全幅）。

## 2. 要望2 コピー元の選び方

### 2.1 利用コンテキスト

| 項目 | 分析 |
|---|---|
| 誰が | 同じコーチ |
| いつ | 練習の前夜か当日朝。場面D 曜日固定の練習を組む（毎週）／場面E 前回の続きを組む（毎週）／場面F 去年の同じ時期を持ってくる（年に数回） |
| どこで | 自宅で右手だけのスマホ、または机のPC |
| どの幅で | 320 / 375 / 414 / 768px。編集パネルの中なので、320pxでは器の幅が本文より狭い |
| なぜ | 一から書くより、前にやった日を持ってきて直すほうが早い |
| どのくらい | DとEは10秒（選んで取り込む）。Fは30秒（年月で絞って選ぶ） |

現状の select 全件一覧は、保存済みの日が増えるほど一覧の長さが伸びる。
1年で100件前後になり、OS のピッカーを回して目当ての日を探す時間が伸びる。
場面Dは最も多いのに、直近の火曜が一覧のどこにあるかを毎回探す。

### 2.2 カスタマージャーニー

#### 意図のフロー

```
場面D 曜日固定の練習
  認知「明日は火曜、半面」→ 動機「先週の火曜を持ってきて直そう」→ 行動開始 編集を開く
  → タスク遂行 おすすめの「直近の火曜」を選ぶ → 取り込む → 直す → 保存
  → 結果確認 日ヘッダとタイムラインに反映 → 行動変容 印刷して持っていく

場面F 去年の同じ時期
  認知「新人大会3週前」→ 動機「去年の3週前の日を持ってこよう」→ 行動開始 編集を開く
  → タスク遂行 おすすめの「去年の同じ頃」があればそれ、無ければ探すで年月を去年の11月にして日を選ぶ → 取り込む → 直す → 保存
```

#### 身体動作フロー（場面D、片手スマホ、320px）

1. 日レベルで火曜を出し、操作列の「編集」をタップする（0.4秒）。編集パネルが開き、見出しに「この日を編集（2026/09/08（火））」が出る。
2. 男女オンリーの3択の下に「他の日からコピー」があり、「おすすめ」の1行目に「直近の火曜　2026/09/01（火）　シュート強化」がある。視線は3択から下へ落ちて1行目で止まる（0.5秒）。
3. 1行目を親指でタップする（0.4秒）。行全体が押せるので、丸い印を狙わなくてよい。
4. 行のすぐ下の「この日を取り込む」をタップする（0.4秒）。中身が空なので確認は出ない。
5. ねらい、コート、時間割が入る。パネルの脚に「2026/09/01（火）の内容を取り込みました」が出る。視線は時間割へ（1秒）。
6. 直して「保存」（1〜3分）。

タップは2回で、現状の「select を開く、一覧を回す、選ぶ、取り込む」の4動作から2動作減る。
減るのは回す動作で、これが一覧の長さに比例して伸びていた。

#### 身体動作フロー（場面F、片手スマホ、320px）

1〜2は場面Dと同じ。

### 2.5 UIデザイナーへのインプット

#### レイアウト制約（行動分析から導出）

- 「他の日からコピー」の枠は3択の下、叩き台の上のまま。取り込みボタンは .ed-mini「この日を取り込む」1つで、枠の最後に置く。
- 「おすすめ」は上から「直近の同じ曜日」「前回の練習日」「去年の同じ頃」の順で固定し、無い項目は詰める。3件を超えない。
- おすすめの各行は行全体が押せる（label）。高さ44px以上。入力部品なので状態ロール（オレンジの塗り）は借りず、カード面と弱い罫線、入った印は本文前景の丸で示す（component-spec.md「入力部品は状態ロールを借りない」）。
- 関係語は12px 700の見出しラベル色、日付は14px 600の本文色、タイトルは14pxの弱い前景。
- 「探す」は年月と日の2つの select（.ed-sel 流用、高さ44px）。年月を変えたら日の選択肢を入れ替える。
- 選択は1つの持ち場。おすすめと探すのどちらかにしか印が立たない。
- 確認は既存の流れ（中身があるときだけ）。文言は3章。

## 4. 設計文書との差分

**「今週へ戻る」の出現条件**。
service-design.md 5.2節は「窓が過去側にあるときだけ現れる」とし、同5.1節の状態2は「前の週を1回押した後に現れている」とする。
1回押した後の窓は今週を含むので、この2つは両立しない。
本分析では「表示中の週が今週でないとき」に現れるとした。
コーチが欲しいのは「いま今週にいない」の合図と戻る入口で、それは窓の位置ではなく選んでいる週で決まる。
未来週（今週＋1〜3週）を選んだときにも現れるが、害は無い。
モックの状態2と6はこの条件で描いた。
窓の位置で決める案に戻す場合、状態2では「今週へ戻る」が消え、状態6でも消える。

**320pxでの一歩移動の置き場**。
5.2節は「320pxで一歩移動と4枠が同じ行に収まるかを最初に確かめる。収まらない場合はタブのラベルを短くするのではなく、一歩移動の幅を詰める」とする。
確かめた結果、詰めても収まらない（1.3節）ので、414px未満は列の上段へ回した。
ラベルも4枠も変えていない。

**上書き確認の姿**。
3.4節は「現状の確認のまま」とする。
現状は window.confirm で、文言は「いまの内容を、選んだ日の内容で上書きします。よろしいですか？」である。
モックは確認カード（.ed-cd）の姿で、写る元の日付と写るものを名指す文言にした。
カードへの載せ替えは行の削除と同じ部品を使うが、本要望の範囲外で、文言だけ先に決めた。
実装が confirm のままなら見出しの1文をそのまま使う。
