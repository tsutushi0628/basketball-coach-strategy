# 押せる部品の色体系の裁定（5回目）

4回目の裁定を実装前レビューにかけた結果を受けて書き直したものである。
用途の正本は `docs/design-system/component-spec.md`、値の正本は `ui/styles/tokens.css` で、この文書は両方をどう書き換えるかを決める。
この文書の適用範囲は押せる部品の色だけで、レイアウト、書体、余白には触れない。

## 1. この裁定が答えている不満

オーナーの差し戻しは一文である。

> だからさ、なんで押せるボタンにいっぱい色があるの？　意味不明なんだけれど

不満の実体は、押せる部品の上に色みを帯びた色が4系統も乗っていて、どれも意味を担っていなかったことである。
現物の値で示す。

彩度差（sRGBの最大チャンネルと最小チャンネルの差を255で割った値）で並べると、押せる部品に使われている色は次のようになる。

| 色 | 実値 | 彩度差 | 押せる部品での使われ方 |
|---|---|---|---|
| アクセント | `#ef7a32` | 0.741 | 選択中の面、確定の面 |
| アクセント深色 | `#a8480c` | 0.612 | 選択中の輪郭、押せる文字11箇所 |
| 赤茶 | `#b8623b` | 0.490 | 行と項目の削除口 |
| 赤茶深色 | `#93502c` | 0.404 | 破壊ロールの枠と文字 |
| 日曜色 | `#a03f3b` | 0.396 | 曜日ピルの文字 |
| 土曜色 | `#31658a` | 0.349 | 曜日ピルの文字 |
| 本文色 | `#2a201a` | 0.063 | 中立の文字 |
| 弱い前景 | `#6d5c4e` | 0.122 | 移動の記号、未選択の文字 |
| 死に色 | `#a08b74` | 0.173 | 押せない部品の全要素 |

上位6色のうち、意味を持っているのはアクセント2色だけである。
赤茶2色は正本自身が3箇所で「弁別には数えない」と宣言していた（`docs/design-system/component-spec.md:83,130,139`）。
曜日2色は、曜日名の文字がすでに同じことを言っている。
つまり色みの中間段（彩度差0.35から0.49の4色）は、画面の上で仕事をしないまま4系統ぶん並んでいた。

この裁定は、その4色を押せる部品から取り除く。
残るのはアクセントと、彩度差0.18以下の暖色階調ひとつになる。

## 2. 押せる部品の色の決まり（結論）

押せる部品に出る色は2系統だけになる。

**アクセント**：選ばれている、決める。
器の中の選択中1個ずつと、編集パネル内の確定1個にだけ塗る（`component-spec.md:86-88` の個数規律を維持する）。

**無彩に近い暖色階調**：それ以外のすべて。
中立操作、破壊、移動、文字だけの導線、押せない状態は、彩度差0.18以下の階調（本文色、弱い前景、死に色、カード面、地の面、罫線）だけで描く。

役割の見分けは色に預けない。
中立と破壊は記号（ゴミ箱と取消）と置き場所と添える一文で分かれ、移動は形（44pxの正円）で分かれ、文字だけの導線は常時下線で分かれる。
これは既存の裁定（`component-spec.md:82-84,136-143`）をそのまま引き継ぐもので、この裁定が新しく決めるのは「色をそこに足さない」ことだけである。

### 2系統である根拠と、その射程

ここでの軸は、**アクセントとそれ以外を分ける軸**である。
選択中と確定を分ける軸（3.8節）とも、器の中で選択中と未選択を分ける軸（3.9節）とも別のものを指す。

その軸は彩度差である。
既定配色では、アクセント2色が0.612以上、それ以外の押せる部品の色が0.173以下で、あいだの0.18から0.61は空になる。
この帯に何も残らないことが、コーチが覚える色が2つで済むということの実体である。

色相では説明できない。
既定配色でアクセント（22.9度）、アクセント深色（23.1度）、本文色（22.5度）、弱い前景（27.1度）、死に色（31.4度）、赤茶2色（18.7度と21.0度）はすべて19度から31度の1本の帯に入る。
同じ帯に入っているものを色相で分けることはできない。
4回目の裁定が根拠にした「押せる要素の色相は[30,75]ビンのみ」という測定は、全部が1つのビンに入るという事実であって、2系統に分かれるという事実ではない。

アクセントとそれ以外を彩度差で分ける説明には、成立する範囲に限りがある。
チームカラーのプリセット16通りでアクセント2変数の彩度差を計算すると、15配色では0.243以上で階調の上限0.18を超えるが、炭色配色（charcoal）だけはアクセント0.051、アクセント深色0.039で、階調のなかに沈む。
したがって彩度差は15配色で軸になり、16配色すべてでは軸にならない。

アクセントとそれ以外を全16配色で分けるのは、正本がすでに持っている**塗りの有無と輪郭**である（`component-spec.md:222,231-254`）。
選択中と確定だけが面を塗られ、アクセント深色の輪郭を持つ。
それ以外の押せる部品は面を塗らない。
輪郭と未選択の面の弁別比は16配色全件で最小5.62、地に対して最小5.39ある。
炭色配色ではアクセントが暗い石板色（`#3a3f47`）になり、カード面に対する比は10.20で、面だけで十分に立つ。

この裁定の「押せる部品の色は2系統」という言い方は、彩度差については15配色、塗りの有無については16配色全件で成立する。
これらの数字は `ui/styles/tokens.css` と `ui/color-presets.mjs` の実値に対する計算であって、実描画で測ったものではない。
製品全体が2系統になったことの確認は、部品CSSの付け替えが終わったあとの再測定に紐づける（7章）。

### 4回目の裁定の「劣化条件で色が最後まで残る」との関係

4回目の裁定は、白黒化とぼかしと縮小の劣化条件では色が最後まで残り記号が最初に落ちる、という実測を根拠に赤茶を残す方向を検討した経緯を持つ。
その実測自体は否定しない。
ただし赤茶を落とす理由は劣化条件での残りやすさではなく、**赤茶が担っている意味が無い**ことである。
残りやすい信号であっても、それが何も指していなければ、読み手は意味を探して外す。
オーナーの差し戻しはまさにその状態を指していた。

## 3. 項目別の決まり

### 3.1 曜日帯から土日の色を落とす

押せる曜日ピルから土曜色と日曜色の参照を落とす。
落とすのは押せる部品から参照される経路と、どこからも参照されていないロールに限る。

**プリミティブ `--sat` と `--sun` は残す。**
この2本は配色設定の検査が構造色として使っており（`ui/color-presets.test.mjs:41` の据え置き対象一覧、`ui/block-tint.test.mjs:25` のトークン一覧）、削除すると2つの検査が落ちる。
4回目の裁定が書いた「全探索の結果ほかに参照が無く孤児化する」は事実に反するので、この文言は使わない。

削除するのは次の4本である。

| 対象 | 参照元 | 削除の可否 |
|---|---|---|
| `--on-saturday` `--on-sunday` | `tokens.css:102` の定義と、正本 `component-spec.md:59,61` の前景ロール列挙のみ | 削除する |
| `--fill-saturday-soft` `--fill-sunday-soft` | `tokens.css:103` の定義のみ。参照ゼロ | 削除する |
| `--sat-soft` `--sun-soft` | `tokens.css:103` と `ui/block-tint.test.mjs:25` | 残す。検査のトークン一覧が参照している |
| `--sat` `--sun` | 上記2検査が構造色として参照 | 残す |

#### 週末を伝えるのは曜日名の文字だけである

4回目の裁定は「週末は曜日名と帯の両端の位置が伝える」と書いた。
帯の両端は根拠から外す。

正本 `component-spec.md:151` が定めているとおり、7日は320pxから414pxで2段に折り返す。
2段になると視覚上の端が4つできる。
4分割と3分割に折り返せば1段目の右端は水曜、2段目の左端は木曜で、端の半分が平日を指す。
折返し位置は使える幅で動くので、どの曜日が端に来るかは幅ごとに変わる。
端の位置は週末を指さない。

したがって週末の伝達軸は**土と日の文字そのもの**の1本だけにする。
1本で足りる根拠は、曜日名が7日すべてに常時出ていて（`component-spec.md:150` の横スクロール禁止条項）、幅によって消えないことである。

#### 帯の並び

帯は日曜始まりにする。
日曜始まりにすると、1段のときは左端が日曜、右端が土曜になり、暦の並びと画面の並びが一致する。
これは週末を伝えるためではなく、コーチが紙のカレンダーと突き合わせるときに読み替えが要らないようにするためである。

### 3.2 確認カード

破壊は色で警告せず、押した瞬間に失うものの名前を出して止める。

#### 姿

| 部位 | 指定 |
|---|---|
| 覆い | `--scrim-overlay` |
| カード面 | `--surface-card`、角丸14px、枠1px `--line-hairline` |
| 内側余白 | 18px 20px |
| 最大幅 | 360px |
| 狭幅の幅 | `calc(100% - 32px)` |
| 見出し | 17px 700、`--on-surface`。失う対象の名前を書く |
| 本文 | 14px 400、`--on-surface` |
| ボタン行 | 右揃え、gap 8px、折返しなし |
| やめる | 中立ロールの素の箱。文字は折り返さない |
| 実行 | 中立ロールの箱にゴミ箱または取消の記号18px stroke1.8。文字の折返しを許す |

見出しと本文をどちらも `--on-surface` にするのは、本文が「何が失われるか」を名指す文で、補足ではないからである。
弱い前景に落とすと、カードで唯一読ませたい情報が最も弱くなる。

#### 覆いの濃さを上げる

現行の `--scrim` は `rgba(42,32,26,.32)` で、この上にカード面 `#fffaf2` を置いたときの面と面の弁別比は2.04である。
正本 `component-spec.md:214` が定める面と面の下限は3:1なので、現行値は下限を割っている。

`rgba(42,32,26,.50)` に上げると弁別比は3.25になり、下限を満たす。
0.48で3.07なので下限は0.48近辺にあるが、丸めて0.50を採り、余裕を持たせる。

この覆いは確認カードだけのものではない。
同じ `--scrim` をドリル詳細のシート（`ui/styles/pattern-timeline.css:242`）と目標編集のオーバーレイ（`ui/styles/goal-editor.css:26`）が使っており、どちらもカード面が `--surface` なので同じ2.04で同じ下限割れを起こしている。
プリミティブを1本上げることで3面が同時に下限を満たす。
これは同型の欠陥が3箇所にあることを確認したうえでの根治で、ついでの最適化ではない。

#### 狭い画面での成立

左右の余白を26pxずつから16pxずつに詰める。
**ボタン行は折り返さない。**
やめるが左、実行が右の横並びを、どの幅でも変えない。

```css
.rc-actions{display:flex;flex-wrap:nowrap;justify-content:flex-end;align-items:stretch;gap:8px}
.rc-actions>.rc-cancel{flex:0 0 auto;white-space:nowrap}
.rc-actions>.rc-exec{flex:0 1 auto;white-space:normal;text-align:center}
```

幅が足りなくなったときに縮むのは実行ボタンの文字である。
実行ボタンから折返し禁止の指定を外し、文字が2行になってボタンの高さが伸びる形にする。
やめるは `align-items:stretch` で同じ高さに追従する。

行を折り返さないのは、折り返すと見た目の上下とDOMの順が逆転するからである。
実行を上に見せようとすると、目で見る順は実行、やめるの順になるのに、Tabキーと読み上げは文書の順のままやめる、実行の順で進む。
削除を止めるための画面で、安全な選択肢がどこにあるかが目と操作で食い違う。
文字を折り返す形なら、見た目の順、文書の順、キー操作の順、読み上げの順が常に一致する。

最も狭い視口で成立することを計算で示す。

| 項目 | 値 |
|---|---|
| 視口 | 320px |
| スクロールバー | 17px（Windowsの実効値。`component-spec.md:176` と同じ前提） |
| レイアウト幅 | 303px |
| カード幅（`calc(100% - 32px)`） | 271px |
| カードの内側余白（左右20pxずつ） | 40px |
| ボタン行に使える幅 | 231px |
| やめる（3字×14px＋内側余白32px＋枠2px） | 76px |
| 実行（最長「捨てて閉じる」6字×14px＋記号18px＋記号と文字のgap7px＋内側余白32px＋枠2px） | 143px |
| ボタン間のgap | 8px |
| 所要 | 227px |

枠の2pxを外寸に足すのは、中立の操作が枠1pxを持つと正本が定めており（`component-spec.md:71`）、幅が `auto` の伸縮アイテムでは `box-sizing:border-box` が外寸に効かないからである。
記号と文字のgapを7pxで数えるのは、モックの中立と破壊のボタンがその値で実装されているためである（`docs/specs/button-roles-20260730.html:40,54`）。

231pxに対して所要227pxで、余裕は4pxある。
1行に収まるので、この幅では文字も折り返さない。

文言がこれより長くなった場合も、実行ボタンの文字が折り返して高さで吸収する。
日本語は文字単位で折り返せるので、実行ボタンが縮める下限は1字ぶんの14pxに記号18pxとgap7pxと内側余白32pxと枠2pxを足した73pxで、そのときの所要は157pxになる。
231pxを下回る経路は残らない。

幅の分岐点をメディアクエリで書かないのは、分岐点を数字で置くと、その数字を測った構成でしか成立しないからである。
文言の長さが変わっても、視口がスクロールバーで15pxから17px狭くなっても、収まらなくなった時点で文字が折り返す。
文字が切れる経路は残らない。

#### 実行ボタンが破壊ロールを参照しないこと

このカードの実行ボタンは中立ロールを参照し、破壊ロールを一切参照しない。
これは設計の欠落ではなく意図である。

カードは1問の全選択肢を並べる場で、2つの答えの強さを色で差をつけない。
強さの差は記号（ゴミ箱と取消）と見出しの一文だけが担う。
実行ボタンに破壊ロールを当てると、将来テーマで破壊ロールを分岐させたとき（3.5節）、削除を止めるための画面で削除ボタンが最も目立つ状態に戻る。
参照しない構造にしておけば、その戻りが起きない。

破壊ロールが無意味になるわけではない。
破壊ロールが仕事をするのは、壊さない兄弟と同じ列に並ぶ引き金（行の削除口、項目の削除口、自動生成に戻す）の側である。
そこでは色の差に仕事がある。

正本の「無害な操作と破壊的な操作を隣接させない」（`component-spec.md:190`）には例外を1文足す。

> 確認カードの2つの答えは例外とする。1問の全選択肢であり、隣接がそのまま比較になる。

#### 確認の文言

| 場面 | 文言 |
|---|---|
| 行の削除 | 時間1（16:00〜16:20）を削除します。 |
| 項目の削除 | この項目（動的ストレッチ）を削除します。 |
| 自動生成に戻す | 手で入れた内容を捨てて自動生成に戻します。 |
| キャンセル | 保存していない入力を捨てて編集を閉じます。 |

対象が空のときは確認を出さず即実行する。

### 3.3 削除口の出し方

削除口は常時表示をやめ、触れているものにだけ出す。

#### 行と項目を分けて出す

4回目の裁定が書いた機構は、行に触れたときに行の中の項目の削除口まで一斉に出る。
現物の入れ子を見ると、行（`ui/editor.mjs:574`）の下に行の削除口（`:585`）と、セルの下の項目（`:534`）とその削除口（`:538`）が両方ぶら下がっている。
`.ed-row:hover .ed-del` はこの両方に当たるので、行に触れると項目5つぶんの削除口も同時に現れる。

行と項目で当てる先を分ける。

```css
.ed-row-top .ed-del,.ed-item .ed-del{opacity:0;pointer-events:none;transition:opacity .12s ease}
.ed-row:hover>.ed-row-top .ed-del,
.ed-row:focus-within>.ed-row-top .ed-del{opacity:1;pointer-events:auto}
.ed-item:hover .ed-del,
.ed-item:focus-within .ed-del{opacity:1;pointer-events:auto}
```

行側は子結合子（`>`）で `.ed-row-top` の直下に限定する。
これがないと、項目の削除口が行の子孫としてもう一度当たってしまう。

項目側は `:focus-within` が単独で効く。
項目にはドリル名とメモの入力欄があり、そのどちらかに触れれば焦点が入るからである。
行側には入力欄のない余白があるので、行には `tabindex="-1"` と、行の `click` で `if(!row.matches(':focus-within')) row.focus()` を当てる。
`pointerdown` はブラウザ既定の焦点処理に剥がされることが実測で確認済みなので `click` を使う。

#### 項目に触れると2つ出る

項目に触れると、その項目の削除口と、その項目を含む行の削除口の2つが出る。
項目は行の子孫なので、項目に触れた時点で行の `:hover` と `:focus-within` も同時に立つからである。
消そうと思えば消せる。
`:has()` を使えば、項目に触れているあいだだけ行側を抑える書き方ができる。

それでも消さずに仕様とする。
出る数は最大2つで、どちらも触れている対象を指しているからである。
1つはその項目を消す口、もう1つはその項目が入っている行を消す口で、コーチが指を置いている場所と両方が対応している。
無関係な削除口が出るわけではない。

行の余白に触れたときは、行の削除口1つだけが出る。
子結合子で行側の対象を `.ed-row-top` の直下に限定してあるので、行に触れても項目の削除口は出ない。

`visibility` と `display` は使わない。
支援技術の読み上げ順から外れ、スワイプ移動で削除口に到達できなくなるためである。
44pxの枠は予約したままにして、出現でレイアウトが動かないようにする。

#### タッチでの2段操作

タッチ環境では1回目のタップが出現、2回目のタップが実行になる。
これは仕様であって不具合ではない。
指で触れているあいだしか `:hover` が立たない環境では、出現と実行を1回のタップに畳むと、狙っていない削除が起きる。
2段にすることで、1回目のタップは必ず取り消せる。

#### 正本の宣言との衝突

正本は「部品を1つ見ればどれかが読める状態にする」と宣言している（`component-spec.md:49`）。
既定で見えない削除口はこの宣言を満たさない。
正本に明示の例外として書く。

> 行と項目の削除口は例外とする。既定では見えず、触れているものにだけ出る。
> 出ていない状態でも支援技術からは常に到達でき、名前を読み上げる。
> 例外を認めるのは削除口だけで、他の押せる部品を既定で隠すことはしない。

### 3.4 押せる文字からオレンジを落とす

押せる要素に乗っている下線なしのオレンジ文字を全廃する。
正本はすでに「下線なしのオレンジ文字を押せる要素に使ってはいけない」と書いている（`component-spec.md:100`）。
その規則に製品が従っていないだけなので、規則は変えず製品を合わせる。

対象は11箇所である。

### 3.5 破壊の姿

#### 2色の割当

破壊ロールは `--terra-ink` 参照をやめ、次のように割り当てる。

| ロール | 値 | 面に対する比 |
|---|---|---|
| `--action-destructive-line`（枠） | `var(--mute)` | カード面6.14、地の面5.89 |
| `--on-action-destructive`（文字） | `var(--ink)` | カード面15.31 |

どちらにどちらを当てるかを書き残すのは、これが正本の記録値を決めるからである。
`--mute-2` の分離条件（`component-spec.md:59-61`）は、前景ロール1本ずつに対する比を記録している。
枠と文字を上のとおりに割り当てると `--on-action-destructive` は `--ink` になり、記録値は「弱い前景の3本が1.96、本文色の5本が4.88」になる。
逆に割り当てると `--on-action-destructive` が `--mute` になり、内訳が4本と4本に変わって記録値が再現しない。

#### 破壊と中立が同じ値になること

この割当により、破壊ロールと中立ロールは枠も文字も同じ値になる。
これは正本がすでに決めていることの帰結である。
正本は中立操作と破壊を同格に置き、強さでは分けず、記号と置き場所と一文で分けると書いている（`component-spec.md:123,129-131,138-140`）。
強さで分けないなら、色でも分かれないのが正しい。

値が同じでもロールは意味の名前として分けて残す。
分けて残すことに実効がある理由は2つある。
1つは、部品CSSがどちらのロールを引いているかで、その部品が壊すものかどうかを読めることである。
もう1つは、将来テーマで破壊だけを分岐させられることである。
たとえば高コントラストのテーマで破壊の枠だけを太く濃くしたくなったとき、ロールが分かれていれば1行で済む。
畳んでしまうと、そのときに全部品を洗い直すことになる。

#### 破壊のミニボタン

`.ed-mini` は汎用の小ボタンで、製品内で7箇所が使っている。

| ファイル:行 | ラベル | 壊すか |
|---|---|---|
| `ui/editor.mjs:497` | この日を取り込む | 壊さない |
| `ui/editor.mjs:506` | 叩き台を読み込む | 壊さない |
| `ui/editor.mjs:553` | ＋ 項目を追加 | 壊さない |
| `ui/editor.mjs:572` | 反転コピー | 壊さない |
| `ui/editor.mjs:612` | ＋ 時間を追加 | 壊さない |
| `ui/editor.mjs:616` | 入力を書き出し | 壊さない |
| `ui/editor.mjs:619` | 自動生成に戻す | **壊す** |

壊すのは1個だけである。
`.ed-mini` を直接書き換えると、壊さない6個も破壊の姿になる。
汎用セレクタには触れず、破壊個体を指す複合セレクタ `.ed-mini.ed-del` を新設して、そこにだけ破壊の様式を当てる。
この複合セレクタは現在CSSに存在しないので、新規に書く。

破壊の様式は中立と同型にする。
12pxのピル土台をやめ、カード面、1px `--action-destructive-line`、14px 600 `--on-action-destructive`、角丸8px、内側余白0 16px、最小高44px、取消記号18px stroke1.8にする。

#### アイコンのみの削除口

`.ed-iconbtn` は製品内で2箇所が使い、どちらも `.ed-del` が付いた破壊個体である（`ui/editor.mjs:538,585`）。
中立のアイコンのみボタンはこのクラスを使っていない。

4回目の裁定は `.ed-iconbtn` に「中立アイコンは `--action-neutral-line`」という指定を書いていたが、その中立アイコンは製品に存在しない。
存在しないものへの指定は書かない。

`.ed-iconbtn` は破壊専用として扱い、30px正方から44px正方へ、枠を `transparent` から1px `--action-destructive-line` へ、SVGを16pxから18px stroke1.8へ変える。
角丸8pxは維持する。

中立のアイコンのみボタンは製品に2個ある（編集ボタン `ui/editor.mjs:47`、コピーボタン `ui/pattern-timeline.mjs:888`）。
どちらも別のクラス `.op-btn--icon` を使っており、すでに44px正方で成立している（`ui/styles/pattern-timeline.css:304`）。
新しい指定は要らない。

### 3.6 hoverで何がどれだけ変わるか

現行の中立と破壊のhoverは面の色だけを `--surface` から `--bg` へ動かす。
この2色の弁別比は1.043で、知覚できない。
面の色だけを変えるhoverは採らない。

hoverの最小量を次のように定める。
押せる部品のhoverは、次の3つのうち1つ以上を満たす。

1. 文字または枠の色が、置かれた面に対する比で1.5倍以上動く。
2. 下線または枠の太さが1px以上増える。
3. 位置が2px以上動く。

各役割の割当は次のとおりで、全役割が1つ以上を満たす。

| 役割 | hover | 満たす条項 |
|---|---|---|
| 状態（未選択） | `translateY(-2px)` | 3 |
| 確定 | `translateY(-2px)` | 3 |
| 中立操作 | 枠を `--action-neutral-line` から `--on-surface` へ（面比6.14から15.31、2.49倍） | 1 |
| 破壊 | 枠を `--action-destructive-line` から `--on-surface` へ（同上） | 1 |
| 移動 | 文字を `--on-action-move` から `--on-action-move-hover` へ（面比6.14から15.31） | 1 |
| 文字だけの導線 | 下線を1pxから2pxへ | 2 |
| 押せない | なし | 対象外 |

確定のhoverは `translateY(-1px)` から `-2px` に変える。
状態と中立がすでに2px動いているので、確定だけ1pxにしておく理由がない。

面だけを動かす3ロール（`--action-neutral-fill-hover`、`--action-destructive-fill-hover`、`--action-move-fill-hover`）は削除する。
どれも `--bg` を指しており、上の3条項をどれも満たさない。
名前だけが残ると「hoverが設計されている」と読めてしまうので、名前ごと消す。

一覧の行リンクのhover（`ui/styles/picker.css:19`）は、枠色を `--hair` から `--orange-soft` へ動かしている。
面に対する比は1.304から1.289で、ほぼ変わらない。
この枠色変化は落とし、同じ行がすでに持っている `translateY(-2px)` だけを残す。
これで条項3を満たし、押せる部品からアクセント系の色が1つ減る。

### 3.7 押せない標識のアクセントは残す

### 3.8 選択中と確定は形が主、器が従

ここでの軸は、**選択中と確定を分ける軸**である。
正本はこれを器の有無に置いている。
実物はそうなっていない。
選択中はピル（角丸999px）、確定は角丸8pxの四角で、確定にはチェック印が付く。
器の罫線は地に対して1.51しかなく、正本自身が「弁別の根拠には数えない」と書いている（`component-spec.md:244`）。

主従を入れ替える。
**形とチェック印が主、器が従**にする。
器は群の範囲を示す補助として残す。

入れ替えは器を主軸と宣言している全箇所に当てる。
1箇所だけ直すと規律が自己矛盾する。
4回目の裁定までに3回連続で出た赤は、すべてこの型の書き残しだった。

対象は正本10箇所とトークン注釈2本である。

### 3.9 器の中の色

4回目の裁定は並べ方の箇条書きに1文を足すとしていた。

> 器の中のピルは選択中以外に色を持たない。

この一文は、見た目の対応表と衝突する。
対応表は未選択にも押せないにも面と枠と文字の色を与えている（`component-spec.md:69,75`）。
文字どおり読むと、対応表の3列が無効になる。

衝突しない形に書き直す。

> 器の中のピルのうち、色みを帯びるのは選択中の1個だけである（既定の配色）。
> 未選択と押せないは、面と枠と文字のいずれも彩度差0.18以下の階調から取り、色みで意味を主張しない。

第1文の射程は2章と同じである。
既定の配色ではアクセントの彩度差が0.741と0.612で、選択中だけが色みを帯びる。
炭色の配色ではアクセントの彩度差が0.051で閾値を下回るので、選択中も色みを帯びない。
その配色では、器の中で選択中と未選択を分ける軸を彩度が担わず、塗りの有無と輪郭が唯一の軸になる。

第2文は16配色すべてで成立する。
未選択と押せないが参照する階調（カード面、罫線、弱い前景、死に色）は配色プリセットの上書き対象外で、どの配色でも値が動かないからである。

現行の値はこの条件をすでに満たす。
未選択の面 `--surface` が0.051、枠 `--hair` が0.110、文字 `--mute` が0.122、押せないの枠と文字 `--mute-2` が0.173である。
落ちるのは土曜色（0.349）と日曜色（0.396）だけで、対応表は1行も変わらない。

彩度差0.18という上限は2章の軸と同じ数字を使っている。
2つの規律で別々のしきい値を持たない。

### 3.10 メモ欄の幅

項目のメモ欄は、モックと製品で幅の決め方が違う。

| 側 | 指定 | 320pxでの振る舞い |
|---|---|---|
| モック `docs/specs/button-roles-20260730.html:219` | `flex:1 1 110px; min-width:0` | 基準幅110pxから空き幅に応じて伸縮する |
| 製品 `ui/styles/editor.css:34` | `flex:1 1 0; min-width:0` | 基準幅0から配分されるので、隣が詰まると潰れる |

4回目の裁定が書いた `min-width:110px` は、どちらとも違う3つ目のやり方である。
これを採ると、項目行が折返し禁止（`ui/styles/editor.css:32` の `flex-wrap:nowrap`）なので、幅が足りないときに行が視口の外へ押し出される。
横スクロールが出る経路を作ることになる。

製品をモック側に合わせる。
`ui/styles/editor.css:34` を `flex:1 1 110px; min-width:0` にする。
基準幅を与えれば潰れず、`min-width:0` を残すので足りないときは縮んで行の中に収まる。
モックは変更しない。

この変更後のメモ欄の実幅は測っていない（7章）。

### 3.11 検査の書き換え

色の規律を変えると落ちる検査が2つある。
期待値だけを新しい値に合わせることはしない。
検査が何を検証しているかを、新しい業務意図に合わせて書き直す。

#### 追従ロールの検査

`ui/color-presets.test.mjs:200-223` は、16配色でチームカラーに追従する意味ロールの集合を検証している。
現行は状態、確定、識別、文字導線、焦点リングの5群を期待し、文字導線として `--on-label-accent` と `--on-link` の2本を数えている。

`--on-link` を `--ink` にすると、この2本は追従しなくなる。
検証する意図を次のように変える。

- 追従ロール一覧（`:50-62`）から `--on-label-accent` と `--on-link` を外す。
- 群の一覧（`:213-219`）から文字導線の行を外し、状態、確定、識別、焦点リングの4群にする。
- 押せる文字が色でなく下線で押せることを示すことを、新しい検証として足す。具体的には、`--on-link` が16配色すべてで値を変えないことと、文字だけの導線を出す5セレクタが `text-decoration:underline` を持つことを検査する。

下線の検査を足すのは、色を落とした結果として下線が唯一の弁別子になるからである。
下線が外れたら押せることが読めなくなるので、外れたら落ちる形にしておく。

### 4.7 ロール参照への付け替え（実装フェーズの本体）

意味ロール層は部品CSSから参照ゼロで、トークンの値を差し替えただけでは画面が動かない。
色の意味が変わる行を直しても、それだけでは足りない。
色を伴う宣言をすべてロール参照へ付け替える工程が本体である。

対象は7ファイル286行である。

数える対象を先に定める。
色を伴うプロパティとは、`color`、`background`、`background-color`、`border` とその方向別ショートハンド4種（`border-top`、`border-bottom`、`border-left`、`border-right`）、`border-color` とその方向別4種、`outline`、`outline-color`、`fill`、`stroke`、`accent-color` である。

枠と輪郭のリセットは数から外す。
`border` 系または `outline` に `none` か `0` だけを与える宣言のことで、色を消す宣言なので色を持たず、付け替える先もない。

## 6. 実装フェーズの完了条件

1. 4章の全表の行がすべて処理されている。処理しない行がある場合は、その行と理由が記録されている。
2. 部品CSS7ファイル286行のうち、色を持つ279行の宣言がロール参照へ付け替わり、直参照のまま残るのは4.7節の4種の例外だけである。色を持たない7行は対象外として記録に残す。セレクタ単位でレビューする。ファイル単位のgrepでは押せる部品と押せない標識を分けられないので、機械検査は補助に置く。
3. 削除口の出る数を数える。行の余白タップ、行番号タップ、Tab移動、タッチ実機相当（`hasTouch`、820×1180のtap）の4経路で、行に触れたときは行の削除口1つだけ、項目に触れたときは行と当該項目の2つまでであることを実測する。3つ以上出たら落とす。
4. 削除口が既定で見えない状態でも、読み上げ用の名前が残っていることを実測する。
5. 確認カードの4文言が出る。対象が空のときは確認なしで実行する。
6. 覆いの濃さを上げたあと、確認カード、ドリル詳細のシート、目標編集のオーバーレイの3面すべてでカード面との弁別比が3:1以上あることを実測する。

8. 押せる部品のアクセント塗りが、器の中の選択中1個ずつと編集パネル内の確定1個だけであることを実描画で数える。

## 7. 測っていないこと

この裁定は次を測っていない。
実装フェーズで測り、結果が裁定と食い違ったら裁定を直す。

**3幅での成立。**
4回目の裁定が記録した320px、375px、414pxの実測（横スクロールゼロ、メモ欄138/193/232px）は、確認カードが無く、曜日帯が日曜始まりでなく、器を入れていない構成で測ったものである。

確認カードを開いた状態、日曜始まりの帯、器を入れた状態で測り直す。

**メモ欄の実幅。**
`flex:1 1 0` から `flex:1 1 110px` へ変えたあとの実幅は計算していない。
320pxで「メモ（」で切れないことを実描画で確認する。

**16配色すべてでの彩度差。**
2章の彩度差は `ui/styles/tokens.css` と `ui/color-presets.mjs` の実値に対する計算で、実描画では測っていない。

0.50に上げると、覆いの下の画面は現行より暗く沈む。

**確認カードを挟んだあとの操作回数。**

**hoverの中立と破壊が同じ見え方になること。**
枠を同じ値に動かすので、hover時に中立と破壊は完全に同じ姿になる。
記号と置き場所で分かれるという設計上はこれで正しいが、実際に押し間違いが増えないかは測っていない。

## 8. 判断11への異見（併記）

PdMが確定させた判断11は「実態は彩度で分離している（アクセントが高彩度、それ以外が低彩度の暖色階調）ので、彩度の軸で書く」だった。
色相の説明をやめて彩度の軸に移すことには同意し、そのとおりに書いた。

ただし「アクセントが高彩度」は16配色のうち15配色で成立し、炭色配色では成立しない。
炭色配色のアクセントは彩度差0.051、アクセント深色は0.039で、階調の上限0.18を下回る。

この裁定では射程を15配色に限定し、全16配色で成立する軸として塗りの有無と輪郭を併記した（2章）。
炭色配色でも選択中の面はカード面に対して10.20あるので、弁別自体は破れていない。
破れているのは「彩度で分離している」という説明の全配色への適用だけである。
